Two pipelines that never call each other. They communicate only by leaving files on disk.

In plain language. There are two completely separate programs here.

The offline one is the librarian. It runs rarely — when you add manuals — and does the slow work: downloading PDFs, cutting them into passages, and converting each passage into a list of numbers. Then it goes to sleep.

The online one is the reference desk. It runs every time you ask a question, and it never writes anything. It just reads what the librarian left behind.

They don't talk to each other. If the librarian crashes halfway through re-indexing, the reference desk carries on answering from the previous shelf, unaware anything happened.

Parsing rebuilds structure the PDF never stored. Chunking cuts on that structure. Embedding turns each passage into coordinates.

In plain language. A PDF doesn't contain paragraphs or headings — only instructions like "print a W at position 45.4, 67.5 in 19.5pt bold." Parsing rebuilds the structure your eye sees automatically.

The lucky break: every Samsung manual carries a built-in table of contents, so we don't have to guess where sections start. Samsung already told us.

Chunking then cuts the text on those section boundaries, never mid-topic. Tiny sections get glued to their neighbours so no passage is uselessly small.

Finally each passage is sent to Gemini, which returns a list of 768 numbers describing its meaning. That list is the "vector."

Same text in, same numbers out. Passages about similar things land near each other.

In plain language. Think of it as giving every passage a coordinate on a giant map of meaning.

Passages about charging land in one neighbourhood. Passages about the camera land in a different one. Nothing about the words themselves is preserved — only what the passage is about.

Later, your question gets a coordinate on the same map. Finding relevant passages becomes finding the nearest neighbours — and that's just arithmetic, which computers do very fast.

This is why the system can match "how do I stop my battery draining" to a passage that never uses the word "draining."

Two files. The text lives in SQLite; the vectors live in FAISS; the chunk's own id is the link between them.

In plain language. Two things get stored, and they must never drift apart.

The words go into a SQLite database — a single file. Alongside them sits a keyword index, the same technology that powers a search box, so exact terms like EP-TA845 can be found literally.

The numbers go into a FAISS file, which is built for one job: given a coordinate, find the nearest ones fast.

The trick that keeps them aligned: a chunk's database id is also its row number in the vector file. There's no separate lookup table to get out of sync — chunk 4,291's vector is simply vector 4,291.

Why the store is swapped, never edited. Re-indexing builds a brand-new directory off to the side and moves it into place only when it's complete. So the reference desk either sees the whole old shelf or the whole new one — never a half-rebuilt shelf. A crash mid-rebuild leaves the working version untouched.

  classDef planned fill:#f5e2c0,stroke:#8a5a1b,color:#2e2618

Both searches run on every question. Neither is trusted alone.

In plain language. Your question gets searched two different ways at once, because each way fails at what the other is good at.

Keyword search is literal. Ask for EP-TA845 and it finds exactly that string. But ask "why is charging slow" and it can't help if the manual says "reduced charging speed."

Vector search understands meaning, so it handles the rephrasing. But it's hopeless at part numbers — to it, EP-TA845 and EP-TA800 mean almost the same thing, which is exactly wrong.

Manuals are full of both kinds of question, so we run both and merge the results. That merger is what "hybrid" in the project name means.

A reranker then re-reads the top candidates properly — slower but sharper — and the best five are handed to Gemini with strict instructions: answer only from these, cite each claim, and if they don't cover it, say so.

The same journey, as a timeline

sequenceDiagram
  autonumber
  participant U as You
  participant App as Chat UI
  participant G as Gemini
  participant DB as corpus.db
  participant FA as index.faiss

  U->>App: "why is my S24 charging slowly?"
  App->>G: rewrite into search queries
  G-->>App: "slow charging", "fast charging not working"
  App->>G: embed the question
  G-->>App: 768 numbers
  par two searches at once
    App->>DB: BM25 keyword search
    DB-->>App: 30 candidates
  and
    App->>FA: nearest-vector search
    FA-->>App: 30 candidates
  end
  App->>App: fuse, then rerank to top 5
  App->>DB: fetch those 5 chunks' text + pages
  DB-->>App: passages with section paths
  App->>G: "answer using only these, cite each claim"
  G-->>App: streamed answer with [1] [2]
  App-->>U: answer + clickable sources

Roughly 1–3 seconds end to end, most of it waiting on Gemini.

In plain language. Note what the database is asked for twice: once to find candidates, and again at the end to fetch the actual text of the winners.

That's deliberate. Searching moves only ids and scores around — small and fast. The bulky text is only fetched for the five passages that survived.

Note also what Gemini is not given: the whole manual. It only ever sees five passages. That's the entire trick behind grounding — it can't invent a settings menu if the only thing in front of it is the real page describing that menu.

5. When each part runs

StageRunsTakesCosts
discoverwhen adding manuals~2 minfree
acquirewhen adding manuals~5 minfree
parse + chunkwhenever tuning~90 sfree
embedonly for new/changed chunks~5 minGemini quota
retrieve + rerankevery message~200 msfree
generateevery message~1–3 sGemini quota

In plain language. The expensive work happens once, offline. Answering is cheap because all the thinking about the manuals was done in advance.

Embedding is the only ingestion step that costs money, which is why chunks are cached by a fingerprint of their content: re-running after a tweak re-embeds only what actually changed, not all 4,630.
